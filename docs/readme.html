Installation

microSRE is a single static binary. No dependencies. No package manager required.

Root or a regular user? While a regular user is enough, running under root may be a better choice when:

  • You want to monitor logs of applications running in Docker containers. Under a regular user microSRE will have to call docker logs --since that becomes slow and IO-intensive for larger logfiles unless log rotation has been set up. When running under root, microSRE can access files directly and keep track of file offsets.
  • You want to gain insight into network connections and files open by processes

curl -fsSL https://microsre.io/install.sh | bash

The installer downloads the latest release, creates a systemd service if systemd is present and starts it up.

To install manually, grab the binary from the releases page and place it anywhere in your $PATH.

Verify

microsre --version

It will display locations of configuration file, logfile and unique machine identifier

Start, stop, restart

Root install - a system-wide service:

sudo systemctl restart microsre
sudo systemctl stop microsre
sudo systemctl start microsre

User install - a user-level service, no sudo:

systemctl --user restart microsre
systemctl --user stop microsre
systemctl --user start microsre

The service is enabled on install and starts automatically - at boot for a root install, at login for a user install. Check status with systemctl status microsre (add --user for a user install).

Quickstart

1. Run microSRE once to create the default configuration file:

microsre --version

As root the config is written to /etc/microsre/config.toml; as a regular user to ~/.config/microsre/config.toml. --version also prints the log file and machine ID locations.

2. Add a webhook to the config to enable alerts:

webhook_url = "https://hooks.slack.com/services/YOUR/WEBHOOK/URL"

3. Verify the configuration:

microsre --verify
# Configuration file valid

4. Watch metrics in the foreground:

microsre --snapshot

The dashboard prints every 60 seconds and shows which alerts would fire. Snapshot mode is a dry run - nothing is sent.

5. Start the daemon:

microsre --daemon

The daemon checks every 60 seconds and sends an alert the moment a threshold is crossed.

Command line

microsre [--snapshot [SECONDS]] [--daemon] [--verify] [--version]
  • --snapshot [SECONDS] - run in the foreground, print the metrics dashboard every N seconds (default 60). Alerts are evaluated and displayed, but nothing is sent.
  • --daemon - run the monitoring loop: check every 60 seconds, send alerts, and report to the hosted view when ingest_url is set.
  • --verify - validate the configuration file: TOML syntax, webhook URL, alert rules, log sources, and template placeholders.
  • --version - show the version and the locations of the config file, log file, and machine ID file.

Run without arguments, microsre creates the default config file if it is missing and exits.

Configuration

microSRE reads a single TOML file. The location depends on the user:

  • root: /etc/microsre/config.toml
  • regular user: ~/.config/microsre/config.toml (or $XDG_CONFIG_HOME/microsre/config.toml)

If the file does not exist, the built-in default is written there on first run with permissions 0600. There is no --config flag - edit the file in place.

Other files microSRE manages:

  • Log file: /var/log/microsre/microsre.log as root, ~/.local/state/microsre/microsre.log as a regular user. Rotated at 10 MB, two backups kept.
  • Machine ID: /var/lib/microsre/machine-id or ~/.local/state/microsre/machine-id. A random UUID that identifies this machine to the hosted view.

Full example

# Report to the microsre.io hosted view (optional)
# ingest_url = "https://eu.microsre.io/ingest?token=<your token>"

# Where alerts go (optional). Slack, Discord and Telegram webhook URLs are
# auto-detected from the URL. No webhook_url - no alerts.
# webhook_url = "https://hooks.slack.com/services/..."
# or: webhook_url = "https://discord.com/api/webhooks/..."
# or: webhook_url = "https://api.telegram.org/bot<token>/sendMessage"
# username = "microsrebot"       # optional display name, Slack and Discord
# chat_id = "-1001234567890"     # Telegram only

[alerts]
# metric name                fire when value >= max for `consecutive` checks
"mem.utilization_pct"    = { max = 90, consecutive = 1, recovery_margin = 0.95, template = "metric" }
"cpu.utilization_pct"    = { max = 80, consecutive = 1, recovery_margin = 0.95, template = "metric" }
"disk.space_usage_pct"   = { max = 90, consecutive = 1, recovery_margin = 0.95, template = "metric" }
"oom.count"              = { max = 1,  consecutive = 1, template = "oom" }
"logs.nginx.error_count" = { max = 10, consecutive = 2, recovery_margin = 0.95, template = "logs" }

[[logs]]
name = "nginx"
path = "/var/log/nginx/error.log"
error_pattern = "\\[error\\]|\\[crit\\]|\\[alert\\]|\\[emerg\\]"

[[docker-logs]]
# containers = ["django-app", "celery-worker"]   # default: all containers
error_pattern = ".(ERROR|CRITICAL|FATAL)."

[[templates]]
name = "metric"
title = "📊 {metric.name} alert on {hostname}"
body = """**{metric.name}**: {metric.value}
**Threshold**: {metric.min} {metric.max}
**Duration**: {metric.consecutive} consecutive checks"""

Top-level keys

  • webhook_url - single destination for alerts. Slack (hooks.slack.com), Discord (discord.com/api/webhooks), and Telegram (api.telegram.org) are auto-detected; any other URL is rejected by --verify. Omit to run without alerts.
  • username - bot display name for Slack and Discord. Defaults to microsre.
  • chat_id - Telegram only, required for Telegram webhooks.
  • ingest_url - report metrics and alerts to the microsre.io hosted view. See Fleet / SaaS.

Alert rules - [alerts]

Each key is a metric name, each value is a rule:

  • max - fire when the value is greater than or equal to this.
  • min - fire when the value is less than or equal to this. Use max, min, or both.
  • consecutive - how many checks in a row the threshold must hold before the alert fires. Default 1. Higher values filter out spikes.
  • recovery_margin - fraction of the threshold the value must return inside before a "Recovered" message is sent. E.g. 0.95 sends recovery once the value drops below 95% of max. Default 0 - the alert state resets silently, with no recovery message.
  • template - name of a [[templates]] entry used to render the message. Required.

Alertable metrics

# memory
mem.utilization_pct  mem.swap_utilization_pct
mem.pressure.{some,full}.avg{10,60}  (+ .previous variants)

# cpu
cpu.utilization_pct  cpu.iowait_pct  cpu.steal_pct
cpu.max_utilization_pct  cpu.max_utilization_core  cpu.utilization_per_core
cpu.loadavg.1min  (+ .previous)
cpu.pressure.{some,full}.avg{10,60}  (+ .previous)

# disk
disk.space_usage_pct
disk.max.utilization_pct  disk.max.await_ms  disk.max.device
disk.total.{read,write}_bytes_per_sec  disk.total.{read,write}_iops
disk.pressure.{some,full}.avg{10,60}  (+ .previous)

# network
net.total.{rx,tx}_bytes_per_sec  net.total.errs_per_sec  net.total.drop_per_sec
net.max.utilization_pct  net.max.utilization_iface
net.max.{rx,tx}_bytes_per_sec  net.max.{rx,tx}_iface

# oom kills - detected automatically from kernel logs, no config needed
oom.count  oom.victims

# per configured log source (logs.NAME / docker-logs.NAME)
<source>.line_count  <source>.error_count  <source>.error_pct

hostname, timestamp, and uptime are also available - mostly useful in templates.

Templates - [[templates]]

Alert messages are rendered with Python format-string placeholders:

  • Any metric name above, e.g. {mem.utilization_pct}. Pressure and load average metrics also have .previous variants with the previous check's value.
  • {metric.name}, {metric.value}, {metric.min}, {metric.max}, {metric.consecutive} - the rule that fired.
  • {scope.*} - fields of the metric family the alert belongs to. For an alert on logs.nginx.error_count: {scope.name}, {scope.error_count}, {scope.error_pct}, {scope.errors} (recent matching lines).
  • {hostname}, {timestamp}, {uptime}.

Placeholders that don't match any known field are reported by microsre --verify.

System Metrics

microSRE reads /proc directly. No shelling out to ps, top, or iostat.

CPU

Source: /proc/stat

CPU usage is calculated by diffing user, system, and idle ticks between intervals. The result is a percentage of total capacity.

Memory

Source: /proc/meminfo

Used memory is MemTotal - MemAvailable. This matches what the OOM killer sees, not what free reports.

Disk I/O

Source: /proc/diskstats

Reads and writes are counted per block device. Space usage comes from statvfs on the root mount.

Network

Source: /proc/net/dev

Bytes and packets in/out are tracked per interface. Dropped and error counters are included in alerts.

Pressure

Source: /proc/pressure/cpu, /proc/pressure/memory, /proc/pressure/io

Pressure stall information (PSI) is available on kernels 4.20+. It measures how much time tasks spend waiting for resources. This is the same signal systemd uses for OOM avoidance.

Log Monitoring

microSRE tails log files and counts lines. Each [[logs]] entry takes a name and an absolute path:

[[logs]]
name = "nginx"
path = "/var/log/nginx/error.log"
line_pattern = ".*"                       # default: every line counts
error_pattern = ".*"                      # default: every line is an error

On every check, each source reports logs.<name>.line_count, .error_count, .error_pct, and .errors (the recent matching lines). Alert on any of them - e.g. max = 10 on logs.nginx.error_count fires when more than 10 error lines appear in a single check.

  • Files are opened and seeked to the end. Existing content is not re-scanned.
  • Log rotation is handled: a new inode or a truncated file resumes from the start of the new file.
  • Patterns are Python regular expressions, matched with re.search - no full-match anchoring unless you add ^ and $.

Example: Nginx errors

[[logs]]
name = "nginx"
path = "/var/log/nginx/error.log"
error_pattern = "\\[error\\]|\\[crit\\]|\\[alert\\]|\\[emerg\\]"
"logs.nginx.error_count" = { max = 10, consecutive = 2, template = "logs" }

This fires when at least 10 error-level lines appear in each of two consecutive checks, and uses the logs template which includes the recent error lines.

Docker logs

[[docker-logs]]
# containers = ["django-app", "celery-worker"]   # default: all containers
line_pattern = "^\\d{4}-\\d{2}-\\d{2}"   # e.g. lines starting with a timestamp
error_pattern = ".(ERROR|CRITICAL|FATAL)."

As root, microSRE reads the container JSON logs under /var/lib/docker/containers directly and keeps file offsets - cheap. As a regular user it falls back to docker logs --since on every check, which becomes slow and IO-intensive unless log rotation is set up. Docker Compose replica suffixes (-1, _1) are stripped, so containers lists service names. Metrics are reported per container as docker-logs.<name>.*.

Multiple log sources

Add as many [[logs]] and [[docker-logs]] sections as you need. Each is independent.

Permissions

microSRE must have read access to the log files. If running as a non-root user, add that user to the adm or systemd-journal group, or adjust file ACLs.

Alerting

Alerts go to a single webhook_url; the chat service is detected from the URL. Omit the key to run without alerts.

# Slack
webhook_url = "https://hooks.slack.com/services/T00000000/B00000000/XXXXXXXX"
username = "microsrebot"      # optional

# Discord
webhook_url = "https://discord.com/api/webhooks/..."

# Telegram - chat_id required
webhook_url = "https://api.telegram.org/bot123456:ABC-DEF.../sendMessage"
chat_id = "-1001234567890"

For Telegram private chats, the chat ID is your user ID. For groups, add the bot to the group and use the group ID (usually a negative number). If Telegram returns HTTP 400, the bot is usually missing channel admin rights.

How alerts fire

  • An alert fires when a value crosses max (or min) and stays crossed for consecutive checks.
  • While an alert is active it is not re-sent. With recovery_margin set, one "Recovered" message goes out when the value returns within the margin.
  • Every alert and recovery is also written to syslog.
  • Message text comes from [[templates]] - see Configuration for the placeholder reference. Telegram messages get MarkdownV2 escaping automatically.

Fleet / SaaS

This is your command and control center with health checks from all your machines in one place

Connecting a machine

1. Sign up at microsre.io to get an ingest URL with a token.

2. Add one line to the top of your config:

ingest_url = "https://eu.microsre.io/ingest?token=<your token>"

3. Restart the daemon. The machine appears in your fleet view within one check, reports a heartbeat every 60 seconds, and sends "up" / "down" events on start and shutdown. If a machine stops checking in, the hosted view alerts - a dead man's switch, not a missing data point.

Troubleshooting

No alerts received

  • Check that the webhook URL is correct and the channel exists.
  • Run microsre --verify to validate the config, and microsre --snapshot to watch which alerts fire in the foreground (snapshot is a dry run - nothing is sent).
  • Verify the machine can reach Slack/Discord/Telegram endpoints: curl -I https://hooks.slack.com

High CPU from microSRE itself

  • The daemon checks every 60 seconds; if it is too heavy, run in the foreground with a slower loop: microsre --snapshot 120 or --snapshot 300.
  • Reduce the number of log files being tailed.
  • Check if a log file is being written to at an extreme rate; microSRE reads every line.

Permission denied on /proc

  • microSRE needs to run as root or as a user with access to /proc. In containers, ensure the procfs is mounted read-only, not masked.

Logs not matching

  • Test your pattern with grep -E 'your-pattern' /var/log/your.log to confirm it matches.
  • Remember that microSRE starts tailing from the end of the file. It will not catch historical lines.
  • Ensure the file path is absolute and the file exists before microSRE starts.

Systemd service fails to start

journalctl -u microsre -n 50 --no-pager

Common causes: invalid TOML syntax, a webhook_url that is not a Slack, Discord, or Telegram URL, a bad regex in a log pattern, or missing read permissions on log files. The config file itself is created automatically on first run - check the path printed by microsre --version.
